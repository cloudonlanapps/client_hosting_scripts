## First-time setup

Once per host. Steps 2, 4 and 5 run on the VPS
(`ssh -p @@SSH_PORT@@ @@SSH_TARGET@@`); steps 1 and 3 from anywhere.

### 1. DNS

A records, all pointing at the VPS (`@@SSH_HOST@@`):

| Name | For |
|---|---|
@@DNS_TABLE@@

The API's record belongs to the API deploy. Check that each one resolves
before going on — certbot fails otherwise:

```bash
@@DIG@@
```

### 2. Web roots (VPS)

```bash
sudo mkdir -p @@WEBROOTS@@
sudo chown @@SSH_USER@@:www-data @@WEBROOTS@@
```

Publishing writes as `@@SSH_USER@@`; nginx reads as `www-data`.

### 3. Publish

```bash
@@PUBLISH_COMMAND@@
```

Besides the sites, this copies `nginx/` and this README to
`~/web_deploy/@@BRAND@@-@@ENV@@/` on the VPS, for the next step.

### 4. nginx (VPS)

```bash
cd ~/web_deploy/@@BRAND@@-@@ENV@@
sudo cp nginx/* /etc/nginx/sites-available/
@@NGINX_LINKS@@
sudo nginx -t && sudo systemctl reload nginx
```

If `nginx -t` warns of a *conflicting server name*, an older vhost already
answers for one of these hosts: remove its link from
`/etc/nginx/sites-enabled/` and reload.

The hosts now answer over plain http:

```bash
@@CHECK_HTTP@@
```

### 5. HTTPS (VPS)

```bash
@@CERTBOT@@
```

Certbot issues each certificate, adds the 443 listener and the http → https
redirect to the files in `/etc/nginx/sites-available/`, and renews them on a
timer (`sudo certbot renew --dry-run` to check).

Copying a regenerated vhost over one certbot has edited drops those edits.
Run the same certbot line again afterwards; it reinstalls the existing
certificate rather than issuing a new one.

### 6. Check

```bash
@@CHECK_HTTPS@@
```
